# Host Browser and Page Stream

## Design Position

Harness UI owns one Chromium process and one persistent profile. Each enabled root Full Control Thread owns its pages and active target. The WebUI presents the selected page through CDP screencast and forwards explicitly authorized page input through CDP. A VNC server, display server, desktop window manager and Playwright driver are not used.

This Chromium-only surface requires WebUI computer sharing. It uses Host filesystem and network authority outside Agent Environment isolation. Harness owns the [Browser Use Capability and CDP adapter](../a13n-harness/23-browser-use.md), Run-local references, page operations and screencast protocol. Harness UI owns browser startup, profile, Thread ownership, viewing admission, human takeover and cleanup. There is no extra Agent loop.

## Host Preparation

The global `browser.executable` setting binds one absolute Chromium executable. Opening browser settings scans installed candidates without selecting one or rewriting settings. `profile_root` defaults to `<data_root>/browsers/profile`, shared across Threads and Projects. Saving either setting requires restarting Harness UI; changing the directory does not migrate or merge profiles. Old VNC executable configuration is ignored.

Readiness requires the configured browser and the optional Python browser dependencies, using cdp-use. Detection is available on Linux, macOS and Windows; actual startup depends on browser compatibility and system libraries. The Host launches Chromium headlessly with a loopback CDP endpoint and a dedicated persistent profile. It passes that endpoint URL to the Harness CDP adapter; WebUI has no independent CDP command implementation. It does not import a personal profile or remove browser profile locks. Installation and browser downloads are never executed by preparation.

## Browser Bindings

Enable creates a process-local binding. Explicit Start or an admitted first navigation launches the shared runtime if needed and creates that Thread's page target. Agent operations use explicit CDP sessions and per-page locks, without a browser-wide operation queue or foreground-window dependency. Popups inherit their opener's Thread and become its active page. Browser tools cannot adopt another Thread's target.

Stop retires the Thread binding and closes its owned targets. Reset closes those targets and creates a new page binding. Other Threads retain their pages and bindings, and the shared process and profile remain alive. Closing the active page stops that binding. Exiting Chromium stops all bindings and requires explicit Start. Old Runs cannot reopen a stopped binding. Process shutdown closes Chromium and its CDP connection; profile persistence does not restore live pages or ownership after restart.

## Viewing and Human Control

Viewing is read-only by default and requires instance-owner authority; scoped guest links expose neither preparation nor streaming. HTTP admission issues a short-lived, single-use viewer ticket tied to the Thread and binding. Viewing admission grants no input authority. CDP endpoints are never sent to clients. A viewer receives frames continuously across takeover and handback. These transitions neither reconnect its WebSocket nor restart its screencast.

Take control blocks new Agent operations globally and waits for existing page operations to settle. Page observations and screenshots for the Agent are unavailable during human control. Handback revokes input authority while preserving viewing access, invalidates old references and requires fresh observation. Waiting tools never replay the action requested before handback. Stopping a Thread wakes its own waiters. Viewer closure does not resume Agent operation without explicit handback.

Screencast prioritizes fresh interaction feedback over retaining every frame and uses JPEG page frames at quality 60. Only binary JPEG messages are sent for pictures; JSON messages carry input rejection or clipboard results. CDP frames are acknowledged independently of individual viewers. Each viewer retains only its latest unsent frame. Delivery uses WebSocket transport backpressure without a per-frame browser-client acknowledgement; stalled writes time out. The client decodes one frame at a time and retains only its latest pending frame, releasing decoded bitmaps after use. Application queues stay bounded, and slow viewers do not stall other viewers. Viewers stop streaming when closed, and the Host stops a target's screencast after its final viewer leaves. Reconnection requests fresh admission and never replays input.

Authorized input is validated mouse, keyboard, text and navigation data, not arbitrary CDP commands. Input reception is independent of CDP dispatch: consecutive pointer moves with unchanged buttons, modifiers and authority retain only the latest position, and consecutive wheel events with the same state accumulate their deltas within validation bounds. Button, key, navigation and authority changes remain ordered barriers. The pending input queue is bounded and backpressures further barriers without dropping them. Coordinates refer to the captured page viewport; the frontend converts from the canvas's displayed size. Each WebSocket input message carries `{control_token, input}`, where `input` is the validated page operation. The Host checks the current token and Thread on every message, including after waiting for the page lock. Stale or missing authority rejects input without ending frame delivery. The first authorized input associates its viewer with the controller; losing that viewer revokes its token and releases held keys while keeping the Agent pause. A later takeover issues a new token, so queued input cannot regain authority. Navigation, back, forward and reload are exposed by the page toolbar. The viewer toolbar contains takeover and an options menu. The menu owns local display zoom, device viewport presets and aspect-ratio selection. Display zoom supports fit-to-panel and 50–200 percent of captured pixels; it does not mutate the remote page or require takeover. Fit mode keeps the page centered. Explicit zoom allows scrolling oversized content while input coordinates remain in the captured viewport.

Viewport changes require current human control. `BrowserViewportRequest.aspect_ratio` defaults to `native`, using the selected device preset's dimensions; selecting a device resets its ratio to that default. Supported overrides are `16:9`, `4:3`, `1:1` and `9:16`. The Host derives height from the preset width and scales both dimensions down if either exceeds 1920, so CDP capture and page input coordinates remain aligned. The selected ratio belongs to the Thread binding and survives Stop/Reset. UI lifecycle buttons are omitted; Host lifecycle operations retain their existing API semantics.

## Presentation Limits

The stream contains page pixels only. Browser chrome, extension popups, native password-manager UI and OS dialogs are not transmitted. CDP screencast does not carry audio. The managed Chromium process starts with audio output muted. Video frames depend on browser capture behavior and are not a media-streaming or WebRTC guarantee.

Page input supports Ctrl/Cmd+A/C/X/V/Z, Ctrl+Y and Ctrl/Cmd+Shift+Z through Chromium editing commands. Copy and cut return the explicitly selected plain text to the controlling viewer, which writes it to the local clipboard with browser permission; password selections are excluded. Clipboard replies are scoped to the current controller token. Paste uses the native browser paste event and inserts its plain-text payload only while the viewer currently owns input; it does not request background clipboard-read permission. Clipboard failures are non-blocking viewer notices. This is not background clipboard synchronization: rich clipboard formats, site-customized copy payloads, cross-origin frame selections, IME and full shortcut portability require separate validation. Native desktop control is unavailable. Password and file filling by Agent tools requires human assistance. Shared profiles retain browser state subject to Chromium and its platform password-store behavior.
